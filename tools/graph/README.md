# 🕸️ The code graph

A local index of every repository in the project: definitions and how they relate. It answers *research* questions fast (where is X, who calls it, what reaches this file, how does A get to B, what implements this trait, what changes together) so scouts and the design skills can map a change before anyone reads a line.

**It is a map, not the territory.** It never answers what code *does* or whether it is *right*: that is read in the code, at the `path:line` every answer carries, before anything is stated, planned or reviewed. The rule and who applies it are in `AGENTS.md` (*The code graph*).

## What it holds

| | |
| --- | --- |
| **Nodes** | files, functions, methods, constructors, classes, structs, interfaces, traits, protocols, enums, types, modules, namespaces, macros (test code is marked, and so is test-support code: Storybook stories, mocks, fixtures) |
| **Edges** | `CALLS`, `IMPORTS`, `EXTENDS`, `IMPLEMENTS`, plus co-change pairs from git history |
| **History** | per-file churn: how many of the last 400 non-merge commits touched the file (commits touching more than 25 indexed files skipped) |
| **Languages** | TypeScript, TSX, JavaScript, Python, Rust, Go, Java, Kotlin, C, C++, C#, Ruby, PHP, Swift (definitions and relations); Vue, Svelte, Scala, Dart, Lua, Elixir, Zig, Solidity, OCaml, Objective-C, shell, SQL, proto, GraphQL, HCL / Terraform (file nodes only, searchable by path) |
| **Data models** | the stores the migrations and schema snapshots declare: tables, fields, keys, indexes and foreign keys, each with the `path:line` of every declaration, and where two declarations disagree ([Data models](#data-models)) |
| **Storage** | one SQLite file, `.grimoire/graph/graph.db` (gitignored with the rest of `.grimoire/`) |

Parsing is [tree-sitter](https://tree-sitter.github.io/) (WASM grammars); storage is Node's built-in `node:sqlite`, so it needs **Node ≥ 22.5**.

### How an edge is resolved

There is no type checker. A call is linked by name, narrowed by what the syntax and the imports say, and every edge records how:

| Confidence | Meaning |
| --- | --- |
| `same-class` | `self.m()` / `this.m()`, or a bare call inside a class, to a member of that class or a supertype |
| `typed` | `x.m()` where the syntax states x's type (a typed parameter, `x = new T()`, `T::new()`, a Go receiver), to a member of `T` or a supertype |
| `qualified` | `Type.m()` / `Type::m()` to a member of that type |
| `import` | the name or its qualifier is bound by an import of the calling file |
| `same-file` · `same-package` | defined in the calling file, or its directory (Go, Java, Kotlin, Swift, C#) |
| `unique-name` | the only definition of that name in the repository |
| `ambiguous` | one of up to three same-named definitions; each gets an edge (`strict: true` drops them) |

`unique-name` and `ambiguous` are the **name guesses**: `graph_status` reports their share per repository, and the page draws them apart (dashed, or hidden until asked). Every other confidence is called *resolved by syntax* here, though `import`, `same-file` and `same-package` still match a name within the scope the syntax gives.

A call on a receiver whose type the repository does not define (a `HashMap`, a `Request`), or a name with more than three candidates, stays unresolved: those go to dependencies. So does a standard-library method name (`len`, `get`, `has`, `map`… listed per language in `COMMON_METHODS`, `lib/langs.mjs`) on a receiver whose type the syntax does not state, and any method on a chain that starts at a type or crate the repository does not define (`Utc::now().timestamp()`, `PutItemOutput::builder().build()`). Without that, the one `len` a repository defines collects every `.len()` in it. **A missing edge proves nothing**: dynamic dispatch, callbacks, reflection, config wiring, string-keyed routes and other repositories are invisible, so "no callers" is confirmed with grep.

## Using it

As MCP tools (the plugin declares the server in `.mcp.json`; agents see `mcp__plugin_grimoire_graph__*`):

| Tool | Answers |
| --- | --- |
| `graph_status` | what is indexed, how much resolved, how many call links are name guesses, what changed since |
| `graph_index` | build or refresh (incremental); `full: true` rebuilds |
| `graph_search` | definitions by name or `*` pattern, files by path fragment |
| `graph_symbol` | one definition: signature, container, members, caller/callee/subtype/test counts |
| `graph_callers` · `graph_callees` | call trees, `depth` 1–5 |
| `graph_impact` | blast radius of a symbol or file: what reaches it by calls, inheritance and imports, grouped by file, the tests on those paths, co-changing files |
| `graph_file` | outline, imports (resolved or external), importers, co-change |
| `graph_hierarchy` | supertypes and subtypes / implementors |
| `graph_path` | the shortest call chain from A to B |
| `graph_data` | the data model: every store, one store's entities, or one entity with its sources and conflicts (SQL tables; key-value tables with their keys, TTL, GSIs and LSIs, billing and stream, from CreateTable files, templates and Terraform); then the refine files' claims, each labelled *refined* and re-checked, their drift, and the gaps ([Refined](#refined-what-no-file-declares-checked)) |
| `graph_changes` | the data model of this branch against its base: added, removed and modified elements (before → after) with `path:line` on each side, and possible renames, never decided; with `delta`, a design's proposed changes, each with its state against the code, then the branch's changes outside them ([Proposals](#proposals-the-delta-beside-a-spec)) |
| `graph_sql` | a read-only `SELECT` for anything else |

Symbols are named as `area`, `Circle.area` / `Circle::area`, `path/to/file.ts:42` (the innermost definition there) or `#id` from an earlier answer. A name matching several definitions answers for each (up to five) and says how to narrow.

From a shell, the same commands:

```sh
node tools/graph/graph.mjs index                 # or: npm run graph -- index
node tools/graph/graph.mjs impact src/auth/session.ts --depth 2
node tools/graph/graph.mjs callers Session.refresh --strict
node tools/graph/graph.mjs sql "SELECT kind, count(*) FROM nodes GROUP BY kind"
node tools/graph/graph.mjs data list [<store>]        # the stores, or one store's entities
node tools/graph/graph.mjs data show books            # one entity: books, drizzle/books or repo:drizzle/books
node tools/graph/graph.mjs data check [<file>…]       # the refine files re-checked; exit 1 on drift or a file that does not validate
node tools/graph/graph.mjs changes [--base main]      # the data model against a base (default: baseBranch, else the base branch, else main)
node tools/graph/graph.mjs changes --delta docs/specs/2026-11-06-loans.delta.json   # a design's changes, each with its state
```

`--root <dir>` points it at another project; otherwise it serves `$GRIMOIRE_PROJECT_DIR`, `$CLAUDE_PROJECT_DIR` or the current directory.

## Seeing it

`node tools/graph/graph.mjs render` (or `/grimoire:graph`) refreshes the index, then writes one self-contained page, `.grimoire/graph/graph.html` (`--out` elsewhere; `--base <ref>` for the Data tab's change overlay; `--delta <file>` for the delta it shows first): an overview; a system map of modules (`lib/modules.mjs`: folders of production code, a folder holding more than 35% of its repository split into its subfolders, linked by the file pairs that use each other through links resolved by syntax, ranked in the order code flows) that opens onto the file-level map (one cluster per directory, laid out once and deterministically by `lib/layout.mjs`); every file and symbol as a neighbourhood, what uses it on the left and what it uses on the right; and hotspots (a size × churn treemap, most called, widest fan-out, most used, co-change), ranked by resolved links. Test code and ambiguous links are hidden until asked for (the system map never shows them); each lane draws its 14 largest modules; every view has a plain anchor (`#sym-12`, `#file-3`, `#mod-4`, `#arch-0`, `#data-1`, `#doc-7`); `#sym-` and `#file-` numbers are index ids that change when that file is re-parsed, and `#mod-`, `#arch-`, `#data-` and `#doc-` numbers follow the order of modules, diagrams, data stores and notes, which shifts as they change: an anchor holds for the index the page was rendered from. No network, no CDN: the page's CSP admits only its own script, by hash. It stays local.

Three more tabs:

- **Architecture** draws the diagrams in `docs/architecture/*.architecture.json` (below) and one drafted from the graph on every render: typed components in their boundaries, labelled lines, a passport per component, upstream and downstream reach, route tracing along the drawn lines, and the code links no line draws. Over a saved diagram, two toggles (one overlay at a time) draw the architecture change view (*The architecture change view*, below): **Changes vs `<base>`** and **Delta**.
- **Data** draws the data model the index read (*Data models*, below): an ERD per SQL store with tables, `#data-<n>` opening the nth of them in `graph_data`'s order. Each table lists its columns (type, `PK`, `FK`, a filled diamond for `NOT NULL`, a hollow one for nullable), its unique keys and declared indexes (the indexes SQLite builds for keys are a count on the store, not rows); a line runs from each foreign key's column (many) to the column it references (one). The layout is computed once per render, in Node and deterministically (`lib/data/layout.mjs`: a table left of the tables that reference it, linked tables grouped, crossings cut by barycentre sweeps, tables with no foreign key last). Search names tables and columns; a click focuses a table, lights it and its foreign key neighbours, and opens its passport: every column, key, index and foreign key (both ways) with the `path:line` of each declaration, linked to the file in the Files tab when it is indexed (`.sql` files are), plain text otherwise. A conflict is badged on its column or table with both values, its tooltip citing both sources. A store of more than 60 tables starts as names only: a focus draws the table with its neighbours, a search the matching tables (40 at most), each with its columns, laid out by the same function; *Columns* draws them all. Under the store picker, the folders found but not read (dialect or order unknown) are listed with their reason, and so are the extractors that failed: the map never pretends to be complete.

  A key-value store is drawn as **key cards**, one per table, not as an ERD (its tables have no foreign key to draw): the table's name, billing, stream and conflict count; its partition (`PK`) and sort (`SK`) keys with their attributes' types (a multi-attribute key as `a S + b S`); its `TTL` (on, off or not said); each `GSI` and `LSI` with its keys and projection; its attributes; the declarations that state it, linked to their files, a template's logical id and name expression beside it; its conflicts, each side with its source. A Terraform table cites the inputs line that states each element and the module's line beside it; a value no file states is drawn as unknown (its `${expression}`, underlined), and a name with such a part carries a *name template* pill. Each row cites the `path:line` of every declaration on hover; a row whose declarations disagree is badged. A card bound to item types (*Item shapes*, below) draws the **item** as a tree by dotted path (each field as each bound type stores it, a key attribute marked `PK` or `SK`, a list `[ ]`, a map `{ }`, an object `{…}`, an enum `E`), each **binding** with its confidence, way, evidence (linked) and rivals, drawn dashed below *convention*, and a pill and a list when it is one declaration of a logical table, with the conflicts across its declarations. Above the cards, the item types the code converts are listed per repository with their tables, the unbound ones badged. With the **access patterns** (*Access patterns*, below; inferred), each index shows the functions that query it (linked to their line, the call's lines and its callers on hover) or a *no access found (lead)* pill whose tooltip says what was searched, a *Reads and writes* list marks each function reading (`R`), writing (`W`), both, or of unknown kind (`?`), each list capped with a count of the rest and the calls that could reach too many tables counted, and a write the bound item does not state joins the card's conflicts; a line above the cards counts the calls and the leads. Search narrows the cards to the tables whose name, attributes, item fields, bound types, indexes or reading and writing functions match. Both overlays mark the cards and their rows as they mark an ERD (added, removed, modified with before → after and, for a change one declaration made, its file; proposed, planned and built, built differently, not in the plan), and each card lists the delta changes it carries. Every name from a file goes into the page as text, never as markup.

  **Changes vs `<base>`**, a toggle above the stores (off by default), draws the branch against its base (*The model against a base*, below): added tables, columns, keys, indexes and foreign keys in green; removed ones struck through in red, a removed table drawn as a ghost box among its foreign key neighbours (the overlay is laid out with them, so it always has a place); modified ones in amber, with before → after on their row and in the passport; possible renames linked, never decided (two tables by a dashed line, two columns or indexes of one table by a bracket beside their rows). A legend says which is which, the store picker counts each store's changes, a store gone from the branch is listed apart, and the passport lists a table's changes with the base's `path:line` as text (those lines are the base's, not the working tree's). The overlay is packed in Node when the page is rendered, against `--base`, else the same default base as `graph_changes`, so the page stays static and network-free; with no base to compare against (not a repository under version control, no such branch), the toggle is absent and the tab says why.

  **Delta**, the other toggle (one overlay at a time), draws a design's proposed changes over the model (*Proposals*, below), with a picker when several deltas sit beside the specs (the newest first, or the one `--delta` names): a proposed table as a dashed green ghost box laid out among the others, a proposed column, key or index as a dashed green row, a proposed foreign key as a dashed line; a proposed removal struck in amber dashes; a proposed change with what it proposes (now → planned); what is planned and built solid green; what is built differently in amber with planned → built on its row; what the branch changed against its base and no change covers in its own colour, *not in the plan* (a removal drawn from the base, struck); a stale acknowledgement badged beside its row. The store lists every change it carries, and a table's passport the ones on it, each with its state, its shape, where it is in the code, its why, its slice and its acknowledgement (who, when; stale once the change was edited). A change whose store is not in the model is listed apart. A delta that does not validate shows its problems and draws nothing. Every string from the file is escaped as the code's own names are. The states are computed in Node when the page is rendered; a static page is read-only, and under `serve` each change can be acknowledged (below).
- **Docs** is every Markdown note of the project (`lib/docs.mjs`: each repository's `.md` and `.markdown` files, the graph's skips and excludes applied, plus the project root's own in a hub), rendered in the page by `lib/md.mjs` (CommonMark's common subset, GFM tables and task lists, Obsidian callouts, `[[wikilinks]]`, embeds as links, tags, front matter as properties; raw HTML only as attribute-free allowlisted tags; linear time on any input, and a note past 200 KB shows as plain text) as a vault: tree and search, outline, backlinks, the indexed files a note names (and, on a file's page, the notes naming it).

Moving around a drawing (`lib/stage-view.mjs`): the file map and the Architecture and Data diagrams pan with a drag on their background and zoom with the wheel. A drag never selects the page around them, not even one that starts on a component or table, and it keeps panning when the pointer leaves the drawing or the drawing reaches its edge, until the button is released; a click (3 px or less) on a file, component or table still opens it. On a touch screen a finger scrolls the Architecture and Data drawings natively and pans the file map. Each drawing is also focusable (Tab, or a click on its background): the arrow keys pan by 60 px, Shift + an arrow by most of the visible size (at an edge, the arrow scrolls the page instead), `+` / `=` and `−` zoom about the centre, `0` fits, and Escape leaves full size. The keys never act from the search box or the passport, nor with Ctrl, ⌘ or Alt held.

### Editing the notes and acknowledging deltas: `serve`

`node tools/graph/graph.mjs serve [--port n]` serves the same page on `127.0.0.1` (`lib/serve.mjs`), re-rendered on every load, with one difference: its Docs tab can save. It prints one address carrying a random access token. It answers only requests that name it as their host (no DNS rebinding) and carry the token (in the page's address, then as a header the page sends: a cross-origin page can neither read it nor send it without a CORS preflight, which is never granted), refuses cross-origin writes and non-JSON bodies, and writes only `.md` / `.markdown` files inside the project's repositories (no `..`, no absolute path, no skipped folder in any letter case, no symlink out, no read-only note), each through a temporary file renamed over it; a note symlinked to another note is written through to its real file, so the link stays, and a symlink whose real file is not itself a note (`x.md → .git/config`, a script, an excluded folder) is refused. A save must name the hash the note was loaded with; one from a copy that changed on disk since is refused with the disk text (409), and the page offers to load it or overwrite. New notes may create their folders, never overwrite. Listing follows the same rule: a symlink out of a repository is never read into the page, served or not. The page's CSP adds `connect-src 'self'`, only when served.

Served, the Data and Architecture tabs' delta overlays also write, and only one thing: acknowledgements. Each change has an *Acknowledge* control (*Acknowledge again* when stale, *Unacknowledge* once acknowledged), and each store (each diagram) one for every change of it not acknowledged yet. A data change and an architecture change are named the same way, by their id (unique across the delta's two lists), and both tabs send the hash of the one delta object they share. They send `PUT /api/delta` `{ repo, path, base, ids, ack }`, under the notes' host, origin, token and JSON-only rules, and the server accepts only `docs/specs/<name>.delta.json` inside a project repository (or the hub root): no `..`, no absolute path, no other extension or folder, no symlink out of it or to a file that is not a delta, no read-only file, never a file it would create. `base` is the hash the delta was loaded with: one that changed on disk since is refused with the disk text (409), and the page offers to reload. A delta that does not validate is never written (422). The server writes each `ack` itself, whatever the request says: `by` the git `user.name` the repository sees, else the system user, on one line and 120 characters at most (a repository's own `.git/config` is not trusted with the file); `at` now; `hash` the change's own (below). It edits only those `ack` members in the text (`lib/data/delta.mjs` `setAcks`), so the file keeps its indentation, line ends and final newline and every other change stays byte for byte; the result is parsed and compared with what was meant before it is written. A layout that in-place edit cannot handle (a key written twice) is rewritten whole instead, after the same check, as JSON in the file's own indentation unit (2 spaces when it has none). Either way it goes through a temporary file renamed over it. The read, the check and the write run under the delta's lock (`lib/data/delta-lock.mjs`), the one the loop's ship step takes to append unplanned changes, so neither writes over the other; held past its wait (30 s), the server answers 503, busy, and the page says so beside the control. Unacknowledging removes `ack`. `serve --delta <file>` picks the delta shown first.

## Architecture diagrams

A diagram is `docs/architecture/<name>.architecture.json` (`graph.architectureDir` moves the folder). [archify](https://github.com/tt-a1i/archify) was the example; the format is grimoire's own, shaped by what the code graph can check and free to evolve with it (no dependency, no compatibility promise): `components` (`id`, `label`, `sublabel`, `type`: frontend · backend · worker · database · messagebus · cloud · security · external · library · cli, `paths` globs of its code, `imports` package prefixes reaching it, `sources` as `repo:path:start-end`, `note`, `tag`, optional `col`/`row`), `connections` (`from`, `to`, `label`, `variant`: default · emphasis · security · async · dashed, `via` for what carries a line the code graph cannot see), `boundaries` (`label`, `kind`, `wraps`) and `cards`. `/grimoire:architecture` writes and refines them.

```sh
node tools/graph/graph.mjs architecture draft [--out <file>] [--title t] [--force]   # a draft from the graph
node tools/graph/graph.mjs architecture check [<file>…]                              # check against the index
```

`lib/arch.mjs` drafts deterministically (one component per module of the system map, typed by folder names and the frameworks it imports, external services from imports of known client libraries, a line per module link resolved by syntax) and checks: the schema, every `paths` glob matching indexed production files, every source existing with its lines, each line between two code components counted in file pairs linked by syntax (or in files importing a component's `imports`), lines the code shows only the other way, code links no line draws, files in two components, and the share of production files covered. It lays a diagram out by flow (a column per step, top-level boundaries as bands, rows ordered to cut crossings, free components placed beside their neighbours outside the bands), unless every component gives its `col` and `row`.


### The architecture change view

The same change view as the data model's (*The model against a base*, *Proposals*), for the diagrams (`lib/arch-change.mjs`, drawn by `lib/arch-view.mjs` from what `lib/arch-pack.mjs` packs in Node).

- **A branch's architectural impact**, against the base `graph_changes` compares with (its merge base with `HEAD`), in two parts. *The diagrams*: `*.architecture.json` read at the base through git (`ls-tree` and `cat-file`, nothing checked out, `lib/data/base.mjs`) against the working tree's: diagrams, components (by id), connections (by their two ends; by their label too where several lines join the same two components) and boundaries (by label) added, removed or modified, before → after per attribute. *The code*: the check's findings (`arch.mjs` `findings`) on the branch's index and not on the base checkout's, each saved diagram of the branch checked against both indexes (so what differs is what the code did): a new link no line draws, a module no component covers, a new external service by import (the check now warns of a known service the code of a component imports and no component reaches through `imports`), a drawn line the code no longer shows. The base index is the base checkout's (`lib/freshness.mjs` `baseIndex`: the checkout `baseOf` names, its index as it was last built, read-only, never refreshed from here), and it is compared only where it is the code the branch forked from: per repository, the head that index recorded must be the merge base the diagrams are read at, with no re-parse pending there. A base index behind or ahead of the fork point would report what the base did as the branch's impact (or hide what the branch still has), and implementers act on these findings, so such a repository's code is not compared. With no base index, or one not at the fork point, only the diagram files are compared, and the answer says why with a short reason (`diagram files only, the code not compared (base index not at the fork point): the base checkout's index is at <commit>, the branch forked from <commit>: refresh it (graph.mjs index in <that checkout>) …`); the page says the same without the checkout's path, since a rendered page may be shared. A project that saves no diagram and whose delta proposes no architecture change loads no second index and reads as before (`archScope`: a listing of the diagrams folder now and at the base, nothing more).
- **The delta's architecture changes**: targets `component:<id>`, `connection:<from>-><to>` (an id holds no `>`, so the ends split at the one `>`; `#<label>` after them names one of several lines joining the same two components) and `boundary:<label>`; `after` in the diagram's words (a component `{ label, type, sublabel?, paths?, imports?, sources?, note?, tag?, repo? }`, a connection `{ label?, variant?, via?, note? }`, a boundary `{ kind?, wraps }`; a rename: a component's `{ id }`, a boundary's `{ label }`; a connection has no name: remove it and add the new one). Validated like the data changes (`lib/data/delta.mjs`), the same hash, the same acknowledgement. Their states are computed against the saved diagrams of the working tree, since the diagram is what a branch builds for its architecture: **planned and built** (drawn as planned; a removal gone; a rename with only the new name drawn), **pending** (not drawn yet; a change with what it proposes), **built differently** (drawn in another shape, planned → built, or the branch touched it another way), stale once edited after its acknowledgement; then **unplanned**: the branch's impact no change covers, a diagram change (*drawn in the branch*) or a finding of the code (*in the code, not drawn*). A change covers what names its target; a rename covers the old and the new element and the lines that meet them; a boundary that only wraps or unwraps components the delta adds, removes or renames is covered with them; a planned component's stated `paths` cover a module no component covered, its `imports` a new service.
- **`graph_changes`** ends with an *Architecture* part when the project saves a diagram (now or at the base) or the delta proposes architecture changes: without `delta`, the diagrams against the base and the new findings in the code; with it, each architecture change's state, the unplanned, a summary. `repo` leaves it out (diagrams span repositories).
- **The page**: **Changes vs `<base>`** draws a saved diagram with its elements added (green), removed (red, put back where they stood) or modified (amber, before → after), the code's new links no line draws dotted, a legend and the list. **Delta** draws a design's architecture changes over it in the Data tab's visual language: a proposed component as a dashed ghost placed by the layout (laid out in Node with the others), a proposed line dashed, a proposed removal struck in amber dashes, planned and built solid green, built differently amber, the impact no change covers in its own colour (*not in the plan*), a stale acknowledgement badged; the delta's counts, every change with its why, slice and acknowledgement, the changes no saved diagram can hold listed apart, and in a component's passport the changes that concern it. Served, each change can be acknowledged (`PUT /api/delta`, as in the Data tab: the same lock, rules, 409 and 503 said beside the control, a Reload that reopens the page on the same overlay).
- **Unplanned architectural impact never blocks** (spec D4): the implementer keeps it with the diagram updated in the same branch (as `/grimoire:architecture` does) or reverts it, and reports it in `modelChanges` with its architecture target; `delta-append.mjs` routes an architecture target to the delta's `architecture` list.
## Data models

The index also reads the project's data model from what declares it in the repositories (and, for a database nothing declares, deduces it from the SQL the code sends, labelled inferred), never from a database and never by running the project's code (`lib/data/`). Each extractor names a format, not a project (`lib/data/registry.mjs`), and its facts are stored per file or per folder (`data_inputs`, `data_facts` in `graph.db`); `lib/data/reconcile.mjs` merges them when asked.

- **SQL migration folders** (`extractors/sql-migrations.mjs`), found by content: any folder with a `.sql` file that creates or alters a table or an index, whatever it is called (`drizzle/`, `prisma/migrations/`, `db/sql/`, `storage/schema-changes/`…), with one migration per file or per versioned subfolder (`<version>_<name>/migration.sql` or `up.sql`). Once found, every file of it holding a schema statement (`CREATE`, `ALTER`, `DROP`: a file with only a `DROP` or a view included) is part of it. Down migrations (`down.sql`, `*.down.sql`, a `-- migrate:down` or `-- +goose Down` section) and files with no schema statement (seeds, queries) are left out, and so are test-support folders; a file marking its up section (`-- migrate:up`, `-- +goose Up`) is read from there, its lines kept.
  - *Order*, per tool: Drizzle's `meta/_journal.json` when there is one (only what it lists is ever applied); Flyway's `V<version>__<name>.sql` by version, compared number by number (`V1.1` and `V1_1` before `V2`, `V9` before `V10`; trailing zeros are no part of a version, so `V1`, `V1_0` and `V1_0_0` share one), then its repeatable `R__<name>.sql` files by name, its undo `U<version>__` files never (noted); else the numeric or timestamp prefix of the file or subfolder names, compared as numbers (golang-migrate's and sqlx's `<version>_x.up.sql`, goose's and dbmate's `<version>_x.sql`, Supabase's `<14-digit timestamp>_x.sql`, Prisma's and Diesel's `<timestamp>_name/` subfolders). Names without one prefix scheme (a `V1__` file beside `create_users.sql`), or two sharing a version, leave the order unknown: the folder is listed as such, never replayed in file-name order by assumption.
  - *Schema dumps*: `structure.sql`, `schema.sql`, or any `.sql` file whose header says a database's dump tool wrote it (`-- PostgreSQL database dump`, `-- MySQL dump`, `-- MariaDB dump`: level 3 in `data_inputs`), unless its name is versioned like a migration (a baseline migration that is a dump stays a migration). A dump is the store as the database has it: a declaration of kind **artifact**, of the migration folder beside it (in its own folder, or the one folder of migrations right under it: `db/schema.sql` states `db/migrations`), else of its own folder. Its dialect comes from its header, else the folder's config, else its own markers; its header states the dialect of the migrations beside it too, when nothing else does. A migration tool's own table in a dump (its record of what it applied, by its exact name: `schema_migrations`, `ar_internal_metadata`, `goose_db_version`, `flyway_schema_history`, `_prisma_migrations`, `__diesel_schema_migrations`, `_sqlx_migrations`, Supabase's `supabase_migrations.schema_migrations`, Drizzle's `drizzle.__drizzle_migrations`) is kept and noted as the tool's, never a presence conflict and not counted among the store's tables. Beside a replay of the same store it is listed first, and its form of an element is the one shown, but the replay stays a declaration of its own (spec D2): where the two disagree (a migration the dump does not show yet, the dump not regenerated), the element keeps a conflict with both sides. A dump's elements are cited at the line that creates them (a dump adds its keys and defaults in `ALTER`s at its end).
  - *Dialect*: `graph.data.migrations` in `grimoire.config.json`, a `drizzle.config.*` whose `out` is the folder, Drizzle's journal, Prisma's `migration_lock.toml` or `schema.prisma` datasource, Supabase (Postgres), a dump's header; else sniffed from the SQL's own markers (`readers/sql-dialect.mjs`: `AUTOINCREMENT`, `WITHOUT ROWID`, `PRAGMA`, `STRICT` for SQLite; `SERIAL`, `::`, `$$`, `JSONB`, `TIMESTAMPTZ`… for Postgres; `ENGINE=`, `AUTO_INCREMENT`, `UNSIGNED`, a `DELIMITER` line, backticks for MySQL; the string a `DELIMITER` sets, `END$$` included, is no Postgres `$$`). No marker, or markers of two dialects, is *unknown*: listed, never replayed as SQLite by assumption.
  - *SQLite* folders are replayed into an in-memory `node:sqlite` database, statement by statement (`readers/sql-split.mjs`: Drizzle's `--> statement-breakpoint`, `;` outside quotes and comments), and read back with `PRAGMA table_xinfo`, `index_list`, `index_info`, `foreign_key_list`: exactly what a fresh database gets. Each table, column, key, index and foreign key cites the migration line that created or last altered it. A statement SQLite rejects stops the replay there: the facts so far are kept, labelled *replayed to `file:line`*, with the error. `ATTACH`, `DETACH` and `VACUUM` are never run, and SQLite itself keeps the replay off the disk: no database may be attached (which also stops `VACUUM INTO`) and an authorizer denies `ATTACH`, `DETACH` and the process-wide `temp_store_directory` and `data_store_directory` PRAGMAs, wherever Node provides them, confirmed by a probe on each replay. On a Node with neither, a statement naming one of those keywords stops the replay. An index's expression column is kept as its text, as its `CREATE INDEX` writes it (PRAGMA names none).
  - *Postgres and MySQL* folders and dumps are read statement by statement, never run and never against a database (`readers/ddl.mjs`, spec D9). **The splitter** is one linear pass, each dialect's own rules: `'…'` with `''` (backslashes in `E'…'` and in every MySQL string), `"…"` names, MySQL backticks, `$$` and `$tag$` quoting, `--`, `#` (MySQL) and nested `/* */` comments, MySQL's `/*!NNNNN … */` read as code (as MySQL runs it), `DELIMITER`, Drizzle's `--> statement-breakpoint`, a psql meta-command line (`\restrict …`) as a statement of its own, goose's `StatementBegin … StatementEnd` as one statement, a routine's `BEGIN … END` body kept whole (Postgres' `BEGIN ATOMIC`; MySQL's triggers, procedures, functions and events without a `DELIMITER`), and a body that never closes split again at each `;` so it swallows nothing. It is exported with the tokenizer (`splitSql`, `lexSql`) as the seam other SQL readers use. **The interpreter** replays, in order: `CREATE TABLE` (`IF NOT EXISTS`, schema-qualified names, types as written, `NOT NULL`, `DEFAULT`, inline and table-level `PRIMARY KEY`, `UNIQUE`, `FOREIGN KEY … REFERENCES` with its actions, `CHECK` counted but not modelled, `GENERATED … AS (…) STORED`, `GENERATED … AS IDENTITY`, serials; `LIKE`, `INHERITS`, `PARTITION OF`, `OF` and `AS` noted and not followed, the table then stated in part), `ALTER TABLE` with one action or several (`ADD` / `DROP` / `RENAME COLUMN`, `ALTER COLUMN … TYPE … USING`, `SET` / `DROP NOT NULL`, `SET` / `DROP DEFAULT`, `ADD` / `DROP IDENTITY`, `ADD` / `DROP` / `RENAME CONSTRAINT`, `RENAME TO`, `SET SCHEMA`; MySQL's `MODIFY`, `CHANGE`, `FIRST`, `AFTER`, `ADD INDEX` / `KEY` / `UNIQUE KEY`, `DROP INDEX` / `PRIMARY KEY` / `FOREIGN KEY`), `DROP TABLE` (the foreign keys to it gone), `CREATE [UNIQUE] INDEX` (`CONCURRENTLY`, `IF NOT EXISTS`, `USING`, `WHERE` partial, an expression kept as its text, an unnamed one named as Postgres names it), `DROP INDEX`, `ALTER INDEX … RENAME`, `CREATE TYPE … AS ENUM`, `ALTER TYPE … ADD VALUE [BEFORE | AFTER]`, `… RENAME VALUE`, `CREATE SCHEMA`, views by name, sequences `OWNED BY` a column (a dump's integer column whose default is its own sequence's `nextval` is the serial it was written as), MySQL's `RENAME TABLE`, inline `INDEX` / `KEY` / `UNIQUE KEY` / `FULLTEXT` (an unnamed functional one named `functional_index`, `functional_index_2`… as the engine names it), `ENUM(…)`, `AUTO_INCREMENT`, `UNSIGNED`, the index MySQL makes for a foreign key no index or primary key leads with (named by the foreign key's index name, else its constraint's, else its first column; dropped once a later index serves the key, kept as an ordinary index when the key goes; marked as the engine's, and so is a dump's `KEY` on exactly the key's columns named that way: counted apart, `(+N implicit, for keys)`, compared where two declarations state it, never a presence conflict, and never a part a design has to state), a `COLLATE` or character set, qualified or not (`pg_catalog."C"`), and Postgres' `search_path`. Postgres folds an unquoted name to lower case (a quoted one kept; a table outside `public` is `schema.table`); MySQL's names stay as written. Every other statement (`DO` blocks, functions, triggers, policies, row level security, grants, `COMMENT ON`, `INSERT`, `SET`, extensions…) is **skipped and counted, per file, by kind** (a note on the declaration); one that does not read is noted at its line, never with its text, and the replay is then not complete (compared for what it states, not for what it lacks), as it is when a statement names a table no earlier one creates. Bounded: 8 MB a file, 100 000 statements, 200 000 tokens and 5 000 elements a statement, a nesting of 256, 4 096 columns and 4 096 indexes (keys, foreign keys) a table, a work budget and 10 seconds a replay, past which it stops with a note (the facts so far kept): a megabyte of `(`, a million commas, an unterminated `$tag$` or comment stay linear, and so does a replay of tens of thousands of statements (a name is found in a map, the foreign keys pointing at a table are kept by its name, so a drop or a rename touches only what it changes).
  - *How the engines' names compare* (`model.mjs normType`, `normDefault`, `normExpr`, shared by reconcile, the branch diff and a delta's states; shown as written): in a Postgres or MySQL store, the names the engine holds for one type compare as one (`int4` and `integer`, `character varying(80)` and `varchar(80)`, `timestamptz` and `timestamp with time zone`, `numeric(5)` and `numeric(5,0)`, `integer[][]` and `integer[]`; MySQL's `int(11)` and `int`, `boolean` and `tinyint(1)`, `decimal` and `decimal(10,0)`), a type by its own name whatever its schema. A default and an index's expression column compare through a normal form of their tokens (linear, capped): the casts the engine adds dropped (`'member'::public.role`, `lower(("Email")::text)`), a `public.` prefix on a function, parentheses that group nothing (around one operand, a whole argument, the whole expression; never those that group operators), `interval '1 day'` as `'1 day'::interval`, a string by its value (`E'a\nb'`, `B'0101'`), a number by its value (`1e3` and `'1000'`; `'-5'` and `(-5)`), an unquoted Postgres name folded (`"title"` is `title`, `"Email"` is not `email`), MySQL's backticks and case, its `true` as `1`. In MySQL a unique constraint and a unique index are one object: every unique index is compared, and shown, as the unique key it is.

- **Code-declared SQL models** (kind `code`: what the code says the store is, which its tool turns into migrations; the only declaration a push-only project has). Each is a declaration of the store its migrations go to, so where the schema and the newest snapshot or the migration replay disagree, the element keeps a conflict, both sides cited and named for what it is: *the code model and the migrations or snapshot disagree: a schema edited and no migration generated, or a migration edited by hand* (spec D2; never resolved by precedence). What a code model states, it states in the store's terms (the SQL type, the default the migration writes), so the declarations compare; what it cannot state so (a custom type, a default that is an expression) is kept as written and marked *not compared* (`unstated`). A table the reader cannot read whole (a column built by code it does not follow) is stated *in part*: what it lacks is no conflict.
  - *Drizzle TypeScript schemas* (`extractors/drizzle-ts.mjs`, through the pinned TypeScript grammar, nothing evaluated). Found by content: a source file importing from `drizzle-orm/sqlite-core`, `pg-core` or `mysql-core` and calling a table builder (bit 4 of its level); a file that only re-exports relative modules (a barrel, bit 8) is read for its re-exports. Per unit: a `drizzle.config.*` and the files under it (its `schema`, a file, a folder, a glob or a list, read as text, and what the files it names re-export), else a folder of schema files no config is above. **Store identity**: the config's `out` (default `drizzle`, beside the config), the folder the snapshots and the replay read; a schema file under a config that does not name it, or under none, is a store of its own folder. Read: `sqliteTable` / `pgTable` / `mysqlTable`, `pgSchema(…).table` (`schema.table` outside `public`), a `pgTableCreator` with a literal prefix and suffix, views by name, `pgEnum` (the store's enums); a column's name (the builder's argument, else the property key with the config's `casing`), its type as the snapshot writes it (`text`, `integer`, `varchar(255)`, `timestamp (3) with time zone`, `time(2)`, `numeric(10, 2)`, an enum's name, `enum('a','d''e')`, `int unsigned`, `decimal(10,2) unsigned`, `datetime(3)`, a `customType`'s `dataType()`, `[]` per `.array()`), `notNull()`, `primaryKey()` (not null; a Postgres serial and an identity column too, a MySQL serial only as the primary key), `unique()` (an index `<table>_<column>_unique` in SQLite, a unique key elsewhere, as drizzle-kit keeps them), `references(() => t.col, { onDelete, onUpdate })` (resolved across the unit's files), `default(…)` (a literal as the snapshot writes it: a number as its value, `1.0`, `1e3` and `1_000` as `1` and `1000`; `sql\`…\`` its text), `defaultNow()`, `defaultRandom()`, `generatedAlwaysAs`; `$defaultFn`, `$default`, `$onUpdate` are **computed defaults**, the client's, recorded as written and never evaluated. The third argument, an array or an object: `index('n').on(t.a, t.b)` (an unnamed one named `<table>_<columns>_index`), `uniqueIndex`, `.where(…)` partial, an expression column as drizzle-kit writes it (`sql\`lower(${t.email})\`` → `lower("email")`, backticks in MySQL; another expression `(expression)`), `primaryKey({ columns })` (and the older positional form), `unique().on(…)` (a unique key, but in SQLite the unique index drizzle-kit creates, named `<table>_<names>_unique` when unnamed, the names the builders know the columns by, before casing, as a column's `unique()` is), `foreignKey({ columns, foreignColumns }).onDelete(…)`; checks and policies are not modelled, `.enableRLS()` is ignored. Columns spread from a shared object (`...timestamps`) and built by a helper (`id: id()`, a const arrow returning a column) are read through them. `relations()` is the query API's, app-level only: noted, never a foreign key. A file that does not parse cleanly keeps what parsed, noted at its line, and its schema is then not compared for what it lacks.
  - *Prisma schemas* (`extractors/prisma.mjs`, `readers/prisma.mjs`: a small hand reader, no grammar). Found by content: a `.prisma` file holding a `model`, `view` or `enum` block (bit 16), a `datasource` block making its folder a root (bit 32); a folder of them (Prisma's multi-file schema) is one model, each file belonging to the nearest root at or above it. **Store identity**: `<root>/migrations`, beside the datasource file, where `prisma migrate` writes (or the `migrations.path` a `prisma.config.*` at or above the root states). Read: the datasource `provider` (the dialect; nothing else of a datasource is kept, as its url may hold a secret), `relationMode = "prisma"` (no foreign keys in the database: none modelled, noted), `@@schema`; models (`@@map` the table), fields of a scalar or an enum type as columns (`@map` the column; the type `prisma migrate` writes for the provider, `String` → `TEXT` on SQLite, `@db.*` native types as written; `?` nullable; lists `[]`), `@id` / `@@id`, `@unique` / `@@unique` and `@@index` as the indexes the migrations create (`<table>_<columns>_key` / `_idx`, or `map:`), `@default` in the migration's terms (a string or an enum value quoted, `now()` → `CURRENT_TIMESTAMP`, `dbgenerated("…")` its text; `autoincrement()` no default, `SERIAL` on Postgres), `uuid()`, `cuid()`, `nanoid()`, `ulid()` and `@updatedAt` as computed defaults, `@relation(fields, references, onDelete, onUpdate)` as a foreign key (Prisma's defaults: Restrict on delete for a required relation, SetNull for an optional one, Cascade on update), an implicit many-to-many relation as its join table `_AToB` or `_<name>` (the two sides of a relation paired by its name, both unnamed alike: both lists and neither naming its fields; a list whose other side names its fields is a one-to-many's back side, no table; stated in part: its keys vary with the version), `view` blocks as views (by name), `enum` blocks (`@map`, `@@map`) as the store's enums; `//`, `///` (and `/* */`) comments skipped, composite `type` blocks noted. Bounded like the other readers: one linear pass into tokens and one into blocks, a text past 2 MB refused, a nesting past 32 levels refused at its block, 4 000 blocks and 1 000 fields per block kept; a block that does not parse is skipped and noted with its line alone (never its text), the others read, and the schema is then not compared for what it lacks. A Prisma 8 `contract.prisma` in the same language is read by content like any `.prisma` file; nothing else of that version is specific.

At a base ref, the TypeScript schema files are parsed aside like the item shapes' (`readers/code-aside.mjs`, once per extractor reading a file), so `graph_changes` sees a column added to a schema.

A data input that is a symbolic link to a file out of the repository is never followed: it is listed as found, not read (`data-inputs` in `graph_data` and `graph_status`).

A Terraform table and a CreateTable file or a template are grouped the same way, by the exact evaluated name (`prod-shop-orders` in both).
  - *One logical table, declared in several places* (`lib/data/binding.mjs` `logicalTables`, across every store and repository): the same name template in two stores (`{env}-{project}-orders`), an exact name a template matches on its literal parts (`local-shop-orders`: `readers/names.mjs`, each unknown part a wildcard). Within one repository's store one exact name is already one table; **across repositories a bare name is no evidence**: two repositories that each declare their own `sessions` table keep two tables (no conflict between them, neither's item fields on the other), each noting the other, told apart by where they are declared (`api:dynamodb/sessions`); a later refine file may claim them one. Nothing else groups: `Orders` and `{env}-{project}-orders` stay apart (no letter case folded, no plural, no edit distance), and an exact name two templates match joins neither and says so. The declarations of a group are compared as one table's are, and what they disagree on across members is the group's **conflict** (local-dev against prod: a GSI the CreateTable file declares and the Terraform table lacks), shown on each member and counted once per store.
  - *The environment the infra sets to a table*: a Terraform resource's `environment { variables = { ORDERS_TABLE = aws_dynamodb_table.this["orders"].name } }` (by the table's address, or a value evaluating to its name or template), a template's function `Environment.Variables` with `!Ref` to a table resource or its literal name (`AWS::Lambda::Function`, `AWS::Serverless::Function`, SAM's `Globals.Function`, the Serverless Framework's `provider.environment` and `functions.*.environment`). Kept on the declaration (`env`), for the binding; no other variable, by name or by value.
- **Item shapes, bound to key-value tables** (`lib/data/binding.mjs`; research §5, "the model is a four-part join": the key schema from infra, the item shape from code, the binding, the access patterns): two code extractors read, through the pinned grammars, each `.rs` and `.ts` / `.mts` / `.cts` / `.tsx` file whose content shows a serde derive, a type, a conversion, an environment read or a string constant (`.d.ts` never), re-parsed only when it changes (and, at a base ref, in child processes: `readers/code-aside.mjs`, in batches, a batch that fails read again file by file so a file that kills the reader fails alone). A file's facts (`readers/code.mjs`) are its types, its constants and, when one of them converts an item, its functions.
  - *Rust* (`extractors/serde.mjs`, typeshare's rules read again): the structs and enums that derive `Serialize` or `Deserialize`, as stored: `rename` (or its `serialize` half), `rename_all` with every case style serde knows (a field's from snake_case, a variant's from PascalCase), `rename_all_fields`, `r#type` as `type`, `flatten` (the type's fields inline, under its own rules), `default` (bare, on the container, or the function it names), `skip` and `skip_serializing` (never stored, left out), `skip_deserializing` (kept), `skip_serializing_if` (may be absent), `tag` (beside a struct variant's fields, or a newtype variant's struct's; a newtype of anything else, which serde rejects, noted), `tag` + `content` (each variant's value at the content key: a struct's fields under it, a string or a number the value itself), `untagged` (the struct and newtype variants' fields together), external tagging (one member per variant, its value under it), and a struct's `tag` (its own name stored), `Option` nullable, `Vec` and the sets a list, the maps a map, `Box`, `Rc`, `Arc`, `Cow` what they hold, a newtype or a `transparent` struct what it wraps.
  - *TypeScript* (`extractors/ts-types.mjs`): interfaces and type aliases, `?` and `| null` nullable, a union of string literals an enum, arrays and `Array` / `Set` a list, `Record` / `Map` / an index signature a map, object type literals nested, `extends` and `&` inlined.
  - *Item types*: the types code converts to or from an item, resolved by name among the types of the same language (the converting file's own, else its repository's one, else the project's one; two of one name and none in the file: not resolved, and said; a Rust field typed by a type serde does not shape stays its name, never a TypeScript type of that name), and the types implementing a conversion. A conversion: a call named like one (`to_item`, `from_item`, `from_items`, `to_dynamo_item`, `from_dynamo_item`, `…_item_parser`; `toItem`, `fromItem`…), its type from the turbofish (`from_item::<_, Order>`), the path (`Order::from_item`, `Self::…`), the receiver or argument whose type the function states (a parameter, a typed let, a struct literal, `self`), the let or the `as` it is given, else the function's return type; `marshall(x)`, `unmarshall(item) as T`, an `Item: x` member, `….Item as T`. Only these are modelled, never every struct of a repository; their shape is their fields nested by dotted path (a struct's fields under `field.`, a list's elements' under `field[].`, a map's values' under `field{}.`, six levels at most). Bounded whatever the code holds: a type already being followed, a struct, a newtype or an alias that holds itself directly or not, is a leaf; a type's expansion at a depth is computed once and reused; an item keeps 400 fields and one model 200 000 at most, the shape cut there and noted; pairing goes per type and table, never per conversion and name. A failure while binding never takes a data tool down: the stores are answered as declared, and `graph_data` and the page say the item shapes were not bound, and why.
  - *Binding* an item type to a logical table, each way with its evidence (`path:line`): a **mapper** declaring it (no extractor gives one yet: the hook is a code file's `mappers`), *declared*; an **environment variable** the code reads (`std::env::var("X")`, `env!`, `process.env.X`, directly or through a constant of the file or of another) that the infra sets to the table, in the function that converts the type, *convention*, or only in its file, *name-match*; a **name** the code builds (a literal, a `format!` string, a template literal, a concatenation; each part it fills in a wildcard) that the table's name or template matches on its literal parts, the table's last word spelt by the code (`format!("{}-shop-orders", stage)` and `"test-shop-orders"` match `{env}-{project}-orders`; `{}-{}` never does), in one function or one file, *name-match*. A conversion in test code ranks below every conversion of the code it tests (a test building an item for another table's fixture is a rival, not a tie); a table only test code names (a literal in a test, a variable a test reads) ranks no higher than a name, and its binding says *named only in test code*. A literal equal to an exact table name is evidence in its own repository only (a name with an unknown part, or a template, may bind across repositories). A type with several tables at its best rank is *ambiguous* with each; every other table it pairs with is listed as a **rival**; below *convention*, a binding is drawn dashed. A type no table pairs with is **unbound**. A binding crosses repositories: the infra's tables bind the types of the code that builds their names. Not read yet: Python's `os.environ`, an environment variable a container definition, a `.env` file or a Terraform module other than the tables' sets, a name built through a function of another file.
  - *On the tables*: a binding's item type (not an ambiguous one's) adds its fields to every member of the logical table, as **item fields**: one per stored path, its `item` saying what each bound type stores there (as written, nullable, default), at its code line (source kind `code`); an attribute the infra types too keeps its declarations and gains the item. The diff and the delta address an item field like an attribute: `<repo>:dynamodb/<table>.<field path>` (`infra:dynamodb/{env}-{project}-orders.lines[].qty`), compared on `item`.
  - *`graph_data`* lists the logical tables (with their conflicts across members) and the item types per repository (each table, confidence and way; the ambiguous with all; the unbound); a table shows its item tree (keys marked), its bound types with their evidence and rivals, and the logical table it is one declaration of. **`graph_changes`** reports an item field added, removed or changed.
- **Access patterns, inferred from key-value SDK calls** (`extractors/dynamo-access.mjs`, `lib/data/access.mjs`; the research's fourth part: "which index each query uses, which attributes each update writes"). The least trusted kind, `inferred` (spec D2): it never changes a declared fact. A source file is read only when its content shows a call shape (bit 2 of its level in `data_inputs`), and again only when it changes:
  - *Rust*: an aws-sdk builder chain from the client (`query()`, `put_item()`, `update_item()`…) or a builder type (`Update::builder()`, `Put::builder()`…), its `.table_name(…)`, `.index_name(…)`, `.key_condition_expression(…)`, `.update_expression(…)`, `.projection_expression(…)`, `.expression_attribute_names(k, v)`, `.item(k, v)` and their `set_…` forms (`Some(…)`, `.to_string()`, `HashMap::from([…])` unwrapped); a chain of the project's own builder naming an index, a key condition or an update (`eb.set_index_name(…)`) is a call too. An accessor with no argument, a chain on another operation (`describe_table()`), and a call inside a macro's arguments (`try_join!(…)`, `vec![…]`: a token tree the grammar does not parse) are not.
  - *TypeScript and JavaScript*: an object literal with `TableName`, `IndexName` or `KeyConditionExpression` (an `UpdateExpression` holding a text, beside the item's `Key` or given to an SDK call: alone it is an ESTree visitor's key), its operation from the SDK v3 command it is given to (`new QueryCommand({…})`, lib-dynamodb's `UpdateCommand`…), the DocumentClient method (`doc.query({…})`, SDK v2), a transaction leg (`{ Update: {…} }`), the input type it is declared as (`QueryCommandInput`), else, for a variable, the first call taking it after its declaration within the block that declares it (one pass over the file, then a search per variable), else its keys. A handler assigned to `exports.h` is named so.
  - *Never a call*: what declares a table or an index rather than reaching one: a CreateTable or UpdateTable input (`KeySchema`, `AttributeDefinitions`, `Projection`, `GlobalSecondaryIndexes`, `GlobalSecondaryIndexUpdates`… beside it or above it), a GSI's or an LSI's declaration (`{ IndexName, KeySchema, Projection }`, `GlobalSecondaryIndex::builder()`, `CreateGlobalSecondaryIndexAction::builder()`, a `create_table()` or `update_table()` chain, `types.GlobalSecondaryIndex{…}`, a `CreateTableInput`), the table's administration (`createTable`, `describeTable`, `UpdateTimeToLive`…). Such a GSI no call queries stays a lead.
  - *Python* (boto3): `query`, `scan`, `get_item`, `put_item`, `update_item`, `delete_item`, batch and transaction calls with keyword arguments, on a client (`TableName=`) or a Table (`dynamodb.Table(…)`, in place or through the name or `self.` attribute it was assigned to); `Key("a").eq(…)` conditions. A `query` with no key-value argument (an ORM's) is not one.
  - *Go*: an `aws-sdk-go` or `-v2` input literal (`&dynamodb.QueryInput{…}`, `types.Update{…}`), its fields through `aws.String(…)` and `&x`, `fmt.Sprintf` names with each verb a part filled in.
  - *What each call says*: its operation (query, scan, get, put, update, delete, batch, transaction, condition check), what names its table (as the binding reads names: a literal, a template, an environment read, a constant), its index, its key condition's attributes, what an update writes (SET, REMOVE, ADD and DELETE paths, `#names` resolved through a literal ExpressionAttributeNames, a list index as `[]`; a `#name` the map lacks leaves its path open, not compared), a literal put item's attributes, its projection. A value from a constant of the same file is followed (`.index_name(BY_OWNER)`, `IndexName: Indexes.ByOwner`, an enum's member, a Python class constant through `self.`, `cls.` or the class, a Go package constant); one of another file is resolved through the binding's constant resolution (its file's, else its repository's one, else the project's one, in its language): a name of the file (an import, a top-level name) or one in SCREAMING_CASE, a member only of a module imported whole (`import * as C`, `require(…)`, Python's `import consts`). Anything else (a function's result, a parameter, a match arm, another object's member: `process.env.X`, `cfg.X`, `settings.X`) is kept as unknown, never guessed and never a constant of the same name elsewhere. A file holding no call but string constants (an exported `const`, a module-level SCREAMING_CASE name, a Go `const`) is read for them alone, so another file's call can name them; Rust's are read for the item binding already.
  - *Test code*: the code graph's test paths (`tests/`, `__tests__/`, a `.test.`, `-test` or `_test` file…: `lib/langs.mjs` `TEST_PATH`), and each language's own marks (`#[cfg(test)]`, `#[test]`, `test_*` functions, `Test*` funcs).
  - *Its table*, first found, through the binding's name matching (never fuzzy): the call's own table argument; else its function's names; else its file's; production code over test code. A call naming an index keeps, among those, the tables declaring an index of that exact name; when none do (only the call's own table argument outweighs the index it names), the tables declaring the index stand in. Several at once: *ambiguous*, each listed (the first three named, the rest counted). A call that could reach **more than 5 tables** says too little to attach: it is counted on each (*spread*), never listed, and an index it names is not called unqueried on them (that would be a false lead). A call no table is found for is counted.
  - *Each index* lists the functions that query it, through the code graph's symbols (the innermost function, method or constructor holding the call, its `path:line` and its callers), or a **lead**, never a verdict: `no access found (lead): no IndexName or index_name naming it in the indexed repositories; it may be reached through a constant built elsewhere, another repository, or a script`; or that calls name it only on another table, or only in test code.
  - *A write the item does not state*: an attribute a call reaching one table writes (an update's path, a literal put item's attribute) that neither the item types bound to that table (not an ambiguous binding) nor its declarations (attributes, keys, index keys, TTL) state is an **inferred conflict** beside the declarations' own, `written` against `absent from the item`, both sides cited; it never becomes a field. Into a map, a list's elements, a type the shape does not expand or an attribute only the declarations type, a path is not compared; a table with no item type bound is not compared, and says so.
  - *Bounded*: one file gives at most 400 calls (the walk stops there, said); a table lists at most 25 functions per index, 25 reading or writing it and 25 inferred conflicts, each list with a count of the rest; a function's written attributes and call lines are capped too; the page ships each way a call reached its table once and refers to it.
  - *`graph_data`* says it in one line (calls, files, tables reached, calls counted for reaching too many, leads); with a table, each index with its queries or lead, the functions that read and write it (each with its operations and what it writes; a call of unknown operation counted apart, never as a write), and the inferred conflicts. **Key cards** draw the same: under each index the functions querying it or the lead pill, a *Reads and writes* list, the inferred conflicts; search finds a table by a function's name. **`graph_changes` does not compare access patterns** (left for a later slice: the base would parse its source files a second time aside); a base's files are not read for them.
- **SQL schemas inferred from the queries in code** (`extractors/sql-queries.mjs`, `readers/sql-query.mjs`, `lib/data/queries.mjs`): for a database that has no migrations, dump or schema in the repositories (one that lives only in production, reached by raw SQL), the statements the code sends say most of its model. The least trusted kind, `inferred` (spec D2): never connecting to a database, never running the code, never overriding a declaration.
  - *Found by content* (bit 64 of a source file's level): a query call beside SQL text, or a SQL client import (the architecture's known Postgres, MySQL and SQLite clients, the generic ones such as Go's `database/sql`, sqlx, knex, SQLAlchemy, and a few more: `extractors/sql-queries.mjs` `CLIENTS`, each with the dialect it speaks). Read through the pinned grammars, per language: *TypeScript and JavaScript* calls named `query`, `execute`, `exec`, `prepare`, `raw`, `unsafe`, `$queryRaw`, `$executeRaw` (and their `Unsafe` forms), a tagged template of one of those names or `sql` (`sql\`…\``, `prisma.$queryRaw\`…\``), a config object's `text` (`pool.query({ text })`); *Go* `Query`, `QueryRow`, `Exec`, `Prepare` and their `Context` forms, sqlx's `Get`, `Select`, `Queryx`, `NamedExec`…, the SQL wherever it is among the arguments (after a context); *Python* `execute`, `executemany`, `executescript`, asyncpg's `fetch`, `fetchrow`, `fetchval`, pandas' `read_sql`, SQLAlchemy's `text(…)`; *Rust* sqlx's `query!`, `query_as!` (after its type), `query_scalar!`, the functions `query`, `query_as` (a turbofish too), `sql_query`, rusqlite's and postgres' `execute`, `query`, `query_row`, `prepare`…. The SQL text: a string or template literal, a same-file constant holding one (only what nothing can change: TypeScript's `const`, Go's `const`, Rust's `const` and immutable `static`, Python's module-level ALL_CAPS name assigned once; never a `let`, a `var`, a lowercase Python name, nor one a parameter or a local of a function around the call shadows), a concatenation, Go's `fmt.Sprintf`, Python's `%`, `.format` and f-strings, Rust's `format!`. A text is read only when its first word is a statement's (a query builder's fragment, `sql\`${col} = 1\``, is none), and prose is none (`Select a user from the list`: a capitalised verb is SQL only when the statement keeps that case style to its end and has the clause its verb needs). The content filter, run on every source file, is linear (no two repetitions matching the same blanks); a file is read in one walk down its tree (a call's function, class and test status come down with the walk, never by walking up from the call), within 10 s (past it, said).
  - *Inert*: whatever code fills in (a template's `${…}`, an f-string's `{…}`, a format verb, a concatenated variable) becomes a parameter, never evaluated: a table or a column named by a parameter (`FROM ${table}`, `t_${suffix}`, `${schema}.users`) is never a table or a column, only counted as dynamic; SQL built from variables is read from its literal parts alone. Every parameter style is one: `?`, `?1`, `$1`, `$name`, `:name`, `@name`, `%s`, `%(name)s`. Only identifiers are kept, never a literal's value (a literal may hold a secret), and what is not read is noted by its line, never its text. Two rules keep a value from passing for a name where the dialect is unknown: a `"…"` (a string in MySQL, and in SQLite where no column has its name) is never a name in a value position (the right of a comparison, `IN (…)`, `VALUES (…)`, the right of `SET a =`, `LIKE`, `BETWEEN`, a function's arguments, a `CASE` result), only where a name alone can stand (a column list, a predicate's left side, a qualified name; alone in a select list, in Postgres only); and a backslash before a closing quote (`'it\'s'`, an escape in MySQL and the string's end elsewhere) ends the statement's reading there, said by line, so no word after it is ever taken for a name. (The code graph itself keeps each definition's first line as its signature: a one-line function holding a literal shows it there, as before this extractor.) Test code is not read for the model (its calls are counted).
  - *The statement reader* sits on slice 12's splitter and tokenizer (`readers/ddl.mjs` `splitSql`, `lexSql`), in the file's client dialect: `SELECT` (with `WITH`, `UNION`, subqueries, derived tables, `LATERAL`), `INSERT` (its column list, `VALUES`, `INSERT … SELECT`, MySQL's `INSERT … SET`, `REPLACE`, SQLite's `INSERT OR …`), `UPDATE` (with Postgres' `FROM`, MySQL's joined form), `DELETE` (with `USING`, MySQL's `DELETE t FROM`), `TRUNCATE`, `RETURNING`, `ON CONFLICT`, `ON DUPLICATE KEY UPDATE`; every other statement counted by its first word. Aliases, `schema.table` and `schema.table.column` are resolved within a statement (a subquery sees the aliases around it); a bare column only where one table can hold it (else counted unresolved, never guessed); a CTE's name, a derived table, a table function and the system catalogs (`information_schema`, `pg_*`, `pg_catalog`, `sqlite_*`, `dual`, `mysql.*`, `performance_schema.*`, `sys.*`) are no tables; a table named like a keyword (`groups`, `range`, `rows`) is one wherever only a name can stand, a column named `key` too, and what does not read as a table factor ends a FROM list (no word after it is ever taken for a table); `*` and `t.*` reveal no column; an output alias, a function's name, a keyword, a typed literal's type, an interval's unit and a cast's type are no columns. Bounded: a text past 256 KB is not read, 200 statements a text, 20 000 tokens a statement (its first ones read), a nesting of 64 (deeper parts skipped, `EXPLAIN` on `EXPLAIN` too, said), 512 facts of each kind a statement, 400 calls, 2 000 statements and 20 000 names a file; linear in its tokens.
  - *What it deduces*, each with the `path:line` of every statement that shows it (the first 8, then a count): **tables**; **columns** (from `INSERT` lists, `SET`, select lists, `WHERE`, `RETURNING`, `ON CONFLICT`, joins, `ORDER BY`); **relations inferred from a join** (`JOIN … ON a.x = b.y`, `USING`, an implicit join in `WHERE`, a correlated subquery; composite ones as one, from a conjunction of equalities only: with an `OR` between them, none; the side whose column is `id`, or names the other table, is referenced, else as written), never a foreign key; **unique keys** from an `ON CONFLICT (a, b)` target (an expression in it gives none, and says so); **lookup columns**, compared for equality with a value in `WHERE` (`=`, `IN`, `= ANY`) or in `ORDER BY`: a lead for an index, never an index; **readers and writers** per function, through the code graph's symbols. **Unknown, and said so**: types (but for the casts the code states, `::int`, `CAST(… AS …)`, kept as casts), nullability, defaults and every other constraint.
  - *Which store*, per repository, never across two without evidence: a file's dialect is its own client import's, else a type naming the database (sqlx's `PgPool`), else the repository's clients when they speak one dialect, else its SQL's markers (the DDL sniffer's, and a cast `::`, `ILIKE`, `$1` weakly, `ON DUPLICATE KEY`, `INSERT OR …`). **Attached** to a declared SQL store of the repository only on evidence: the same client (a Prisma client's `$queryRaw` and the Prisma schema's store, `drizzle-orm` and the Drizzle schema's), or the module they share (the deepest common folder, one store's alone); being the only declared store of its dialect, or of the repository, is evidence by elimination and attaches only when the file names a table that store declares (its exact name, folded as the store folds names, never fuzzy), else the queries are a store of their own (`not attached: no table it names is declared in <store>`); a dialect that contradicts the store's never attaches. How they attach and how many of the tables they name the store declares are said with them (`the only declared SQL store in the repository; 3 of 5 tables named are declared`), and in the conflicts they add. Attached, the queries only add an **`[inferred]` conflict** where the code names a table or a column the declarations lack (`named in code (inferred)` against `absent from the declarations`, both cited), and their access sites on the declared tables: the declared model wins. Otherwise the queries are a **store of their own**, `<repo>:sql (inferred, <dialect>)`, named by its clients and dialect, saying why it is attached to none when the repository declares SQL stores; a file of unknown dialect joins the repository's only deduced store, else one of unknown dialect.
  - *Shown*: `graph_data` lists the deduced store (labelled inferred, its clients, what stays unknown, how its dialect is known) and, for a declared store, the queries attached and their conflicts; a store lists its tables (columns seen, unique keys, joins, lookups); a deduced table its columns with the statements naming them, keys, relations, lookups, readers and writers and what is unknown; a declared table its readers and writers and its `[inferred]` conflicts. The **Data** tab draws a deduced store as an ERD under a banner (*deduced from the queries in code, not declared*): dashed table frames, columns *seen in code* (or their cast), nullability as a dashed diamond, relations as dashed lines *inferred from a join*, no FK marker; its passport lists the same; a declared store lists the tables only the code names, its tables the columns only the code names among their conflicts; everything escaped. A client whose queries are read is no **gap**: a client imported by a file whose queries were read, or one of the repository speaking the dialect of a store its queries were read into; a client whose queries are not read (SQL built elsewhere) stays one, and a deduced store covers its own repository only (a declared store covers its datastore everywhere, as before). **`graph_changes` never compares a deduced store** (a base reads no query; the diff is between declarations), nor the queries attached.
  - *Checked against the engine* (a dev-time oracle, never at test time: `postgres:16` in Docker): the statements of `tests/fixtures/sqlq` prepared and planned against a schema built from exactly what was deduced (its tables, the columns seen, the unique keys from `ON CONFLICT`) all pass; each deduced column dropped in turn breaks a statement that names it, and each unique key dropped breaks its upsert (*no unique or exclusion constraint matching the ON CONFLICT specification*): nothing the queries need is missed, nothing deduced is unused.

A replay, a snapshot and a code-declared schema of one folder are declarations of one store. Elements that agree carry every source; where they disagree (a hand-edited migration, a schema edited without a migration), the element keeps a **conflict** with every side and its source: nothing is resolved by precedence, since the disagreement is the finding. Composite primary keys compare as keys. A replay that stopped early is shown but compared with nothing. Primary and unique keys are elements of their own; the indexes SQLite builds for them are counted apart (`13 indexes (+21 implicit, for keys)`).

### Refined: what no file declares, checked

The script extracts; some facts no file declares. An agent (`/grimoire:data-model`) writes them, reading the code, in a **refine file**, `docs/architecture/<name>.data.json` beside the architecture diagrams (`graph.architectureDir` moves the folder), and the script checks every claim on every answer and render (`lib/data/check.mjs`, spec D8). The format, `schema: 1`, `title`, `summary`, and claim lists; an entity is named by its id as `graph_data` prints it (`repo:store/entity`), a citation is `repo:path:line` or `repo:path:start-end`:

- `lineage` `{ from, to, fields: [{ from, to }], why, sources }`: an entity of one store that mirrors one of another (a device's SQLite `events` and the backend's `{env}-{project}-event`), field pair by field pair;
- `relations` `{ from, columns, to, toColumns, why, sources }`: a relation no foreign key states;
- `indexes` `{ entity, index, purpose, sources }`: what an index is for;
- `bindings` `{ item, table, why, sources }`: an item type bound to one table where the script left it ambiguous or unbound;
- `equivalences` `{ tables: [{ repo, name | template, store?, path? }], why, sources? }`: declarations of one logical table no evidence ties (a local-dev `CreateTable` file's `Orders` and the production template `{env}-{project}-order`), each named as written: an exact name, or a template, never both;
- `stores` `{ repo, id, kind, label?, imports?, why?, entities: [{ name, kind?, source, note?, fields: [{ name, type?, source, note? }] }] }`: a store no extractor reads yet (a document collection, a cache, a search index), entity by entity, a citation per field; `imports`, the client packages reaching it, cover its gap.

**The check.** Each citation must resolve inside its repository (a link or a path leading out of it is no file of it), its lines must exist (200 at most), and they must name what the claim states: one of its names (its entities', fields', columns', index's, item type's, a side's), letter case aside and never inside a longer identifier, a template by its longest literal part (`event` for `{env}-{project}-event`), a field path also by its last part. The claim must agree with the extracted model: its entities, fields, columns, index and item type exist (a field of a key-value table includes its bound item's); a foreign key on a relation's columns to another table contradicts it (one stating the same is noted), and so does, on a deduced store, a join the queries in code show on those columns whose referenced side is known (an `id`, or a column named after the other table), said as *a join inferred from the queries at `path:line`*, never as a foreign key; a join taken as written (equal columns, which one references the other unknown: spec D2's least trusted fact) is only a note, never drift; every relation on those columns is compared, the first three disagreeing said, the rest counted; a binding the code states at convention or above to another table contradicts a refined binding (one the code states the same is noted); an equivalence's declarations exist under the names or templates it states, in the file it names; a described store is no store an extractor reads (an extracted store of the same id makes it drift). The check confirms names at lines, not meaning: a citation proves its line names what the claim states, not that the line shows the relation; the agent reads the code before it claims. A claim that fails is **drift**: listed with where it is in the refine file (`indexes[0] (line 25)`) and why, never drawn or listed as a fact; a described store's entity or field that fails is drift on its own, the rest of the store holds. Bounded: a refine file past 1 MB or nested past 16 levels is not read, at most 2000 claims, 20 citations per claim and 500 entities, fields or pairs per list, strings capped, a cited file past 4 MB not read; each cited file read once per check, by its real path whatever its spelling, at most 1000 files and 64 MB in all, a line scanned up to 4096 characters and 64 MB scanned in all (past a limit, a citation is a plain drift saying which); only the format's keys (a `__proto__` or `constructor` key is refused); errors say where, never what a file holds there.

**Equivalences group.** Their citations are checked first (`refineCheck`, the one way graph_data, graph_changes, `data check` and the page check refine files), so an equivalence whose citation fails is drift and groups nothing; reconcile.mjs joins the declarations of each one that holds into one logical table (`lib/data/binding.mjs` `logicalTables`, its `via` saying `refined: <file> equivalences[<n>]`), so their differences are the group's **conflicts** with each declaration's `path:line`, and an item type bound to one is bound to all. The same equivalences group a base's model (`graph_changes`, the change overlay), so a diff compares the code, never what a refine file groups. A key-value table that, in code that was read, no item type is bound to, no call reaches, no name built and no variable the infra sets names, says so: *declared, no code uses this name* (it may be stale; it is never paired by a guess).

**Gaps.** The datastores the production code reaches through client imports (`lib/arch.mjs` `KNOWN`'s databases, and DynamoDB's clients) that no extracted store of a matching dialect and no refined store's `imports` cover, and that are no client of a repository whose queries are read (*SQL schemas inferred from the queries in code*): listed, so the map never pretends to be complete.

**Shown.** `graph_data` lists the claims that hold, each labelled *refined* with its citation, then *Drift* and *Gaps*; a store or entity a refine file describes answers `graph_data` with it; an entity lists the refined facts about it and their drift. `graph.mjs data check [<file>…]` prints each file's drift and notes and the gaps, and exits 1 on drift or a file that does not validate (a gap is never an error). `graph_changes` re-checks the claims on the branch after its data part, so a branch that breaks a citation says so. The **Data** tab draws the same: drift as a badge and a list, the gaps, lineage as lines from one store's entity to another's with their field pairs (a box opens its store), the described stores as cards with each field at its line, a refined relation within a SQL store as a dashed line on its ERD (and in the table's passport), an index's purpose under its row, a key card's logical table marked refined, its *no code uses this name* note; everything escaped.

### The model against a base

`graph_changes` (and `graph.mjs changes`) compares the data model of this branch with its base's, element by element (`lib/data/diff.mjs`, Liam's approach): stores, tables and views, columns, keys, indexes and foreign keys, each **added**, **removed** or **modified** (each attribute that changed, before → after), with the `path:line` that declares it on its side. The elements of an added or removed table are not listed one by one; a store absent from the base is an added store, one absent from the branch a removed one, never an error.

- *The base*: `base` (`--base`) when given, else `baseBranch` in `grimoire.config.json`, else the branch the index is based on (`lib/freshness.mjs`: the upstream, `origin/HEAD`, `main`, `master`), else `main`; compared at its merge base with each repository's `HEAD`, as `git diff base...HEAD` and a pull request are, so what the base gained since the branch left it is not shown as the branch's doing. A ref given that names no commit is an error; a repository where it names none is left out of both sides, and said so.
- *Read through git, nothing checked out* (`lib/data/base.mjs`): the base commit's files (`git ls-tree`), the candidates the index would read, chosen by the same rules and config, read as blobs through one `git cat-file --batch` (`git show <commit>:<path>` without a process per file; binary-safe, capped as the index caps a file), then the same discovery and extractors (`registry.mjs` `extractAll`). The base's facts never enter `graph.db`: they are memoised per process by repository, commit, extractor versions and the config that steers discovery, and recomputed otherwise. The branch side is the index: the working tree, uncommitted edits included.
- *Compared as reconcile compares*: names in any letter case where the dialect's are (SQLite), types lower-cased and blank-collapsed, defaults without one outer pair of parentheses, a key by its role and columns, as a whole. A change of formatting is no change.
- *Key-value tables*: a table and a GSI or an LSI by name, a key by its role and attributes (`partition (memberId)`, `ttl (expiresAt)`), an attribute by name; a table's billing and stream, a TTL's on or off, an index's kind, keys and projection are what is modified. Their declarations are files of equal standing, so each is compared on its own: what one declaration changed is named with its file (`projection in lending/template.yaml: INCLUDE (dueAt, title) → ALL`), and a declaration that now states an element too changes where it is `declared in`. A declaration is compared with the same file on the other side; when one file left and another came (a file renamed, a file of several tables split into one per table), those two are compared; when what is left does not pair and no file is on both sides, the merged values are. So a change made while the file moved is still reported, beside the move. (A SQL element whose declarations disagree is compared by its merged value, the most trusted declaration's.)
- *Rename candidates*: a removed and an added element of the same kind and shape (a table: its columns and their types, in order; a column: its type and position; an index: its columns, uniqueness and partiality; a foreign key: its columns on both sides) are flagged as a possible rename and never decided: both stay a removal and an addition. Several of one shape on each side form one ambiguous group, listed whole, never a guess at which pairs with which.

### Proposals: the delta beside a spec

A design that changes stored data says so in a **delta**, `docs/specs/<date>-<topic>.delta.json`, beside its spec (`roast` drafts it, `to-plan` gives each change its slice; `lib/data/delta.mjs`):

```json
{ "schema": 1, "spec": "docs/specs/2026-11-06-loans-design.md", "architecture": [],
  "data": [{ "id": "returned-on", "op": "add", "target": "api:prisma/migrations/Loan.returnedOn",
             "after": { "type": "DATETIME", "nullable": true }, "why": "know when a loan came back",
             "slice": 1, "origin": "planned", "ack": { "by": "…", "at": "…", "hash": "…" } }] }
```

- *A change*: `id` (unique in the file), `op` (`add`, `change`, `remove`, `rename`), `target`, `after` (the element as it will be), `before` (optional: as the design saw it), `why`, `slice` (optional), `origin` (`planned`, or `unplanned` for one an implementer kept), `ack` (written by `serve`). `architecture` holds the architecture's changes, in the same shape (*The architecture change view*, below); ids are unique across both lists.
- *Targets* address an element exactly as the diff identifies it, so a target resolves where `graph_changes` matches (names in any letter case where the dialect's are, a key by its role and columns, a foreign key by its columns on both sides). `<repo>:<store>` is the store's id as `graph_data` names it (its folder, which may hold `/`); the entity is the segment after its last `/`:

  | Element | Target |
  | --- | --- |
  | a table or view | `<repo>:<store>/<entity>` |
  | a column (dotted when nested) | `<repo>:<store>/<entity>.<column>` |
  | an index | `<repo>:<store>/<entity>/index:<name>` |
  | a key | `<repo>:<store>/<entity>/key:<role>(<column>,…)` (`primary`, `unique`) |
  | a foreign key | `<repo>:<store>/<entity>/fk:(<column>,…)-><table>(<column>,…)` |
  | a key-value table, an attribute | `<repo>:dynamodb/<table>`, `<repo>:dynamodb/<table>.<attribute>` |
  | a GSI or an LSI | `<repo>:dynamodb/<table>/index:<name>` |
  | a partition or sort key, the TTL | `<repo>:dynamodb/<table>/key:partition(<attribute>,…)`, `…/key:sort(…)`, `…/key:ttl(<attribute>)` |
- *`after`*, in the model's words: a column `{ type, nullable, default?, generated? }`, a table `{ kind?, fields: [{ name, type, nullable, … }], keys?, indexes?, relations? }`, an index `{ columns, unique?, partial? }`, a foreign key `{ onDelete?, onUpdate? }`, a key nothing (its target is its shape), a rename `{ name }`. For a key-value table: a GSI or an LSI `{ kind: gsi | lsi, partition?, sort?, projection?: ALL | KEYS_ONLY | INCLUDE, include? }` (an addition states its kind and a GSI's partition or an LSI's sort), a TTL `{ enabled }`, the table's own `{ billing?: PAY_PER_REQUEST | PROVISIONED, stream?: a view type or null }` (a `change` of the table; an `add` may state them beside its `fields`, `keys` and `indexes`). A key-value element several files declare is planned and built only when each has it as planned; a difference only some have names its file. An `add` describes the whole element: what it states is compared (a table's columns, keys, indexes and foreign keys each as a set: one planned and not built, or built in another shape, is a difference), and what the branch builds on a table it adds beyond what the `add` states (a column, a key, an index, a cascading foreign key) is unplanned, unless another change of the delta covers it; so a new table states every key, index and foreign key it will have. A `change` states only what changes; a `remove` has none. Validation names every problem at once: the schema version, an unknown op or key, a target outside the grammar, an `after` missing or holding what the element has not, a missing `why`, a duplicate id.
- *The hash* of a change is the first 16 hex digits of the SHA-256 of its canonical JSON (keys sorted at every level) without `ack` and `slice`: editing what changes or why makes an acknowledgement stale; reordering keys, or giving the change its slice, does not.
- *States*, computed on every read and never written, against the model the index holds and, when one resolves, the branch's base: **planned and built** (the model has the target in the intended shape; a removal, once it is gone; a rename, once only the new name is there), **pending** (not in the code yet: a change the branch has not touched, with what it proposes, now → planned), **built differently** (the target is there in another shape, planned → built, or the branch touched it another way). Apart: the acknowledgement, **acknowledged** or **stale** (its hash is no longer the change's). And **unplanned**: a change of the branch against its base (`graph_changes`) that no change of the delta covers, and each part the branch built on a table the delta adds beyond what its `add` states (a table added whole is one change in the diff: those parts are listed one by one, each named as a target, with the change whose table they are on). With no base, `before` tells pending from built differently, and nothing is unplanned.

`graph_changes` with `delta` (`graph.mjs changes --delta <file>`) lists each change with its state, the `path:line` that builds it, what differs or what it proposes, its why, slice and acknowledgement; then the unplanned changes, each named as a target; then a summary. A delta that does not validate answers with its problems. Without `delta`, `graph_changes` is unchanged.

**Unplanned changes never block** (the loop, and `implement` in a session). An implementer runs `graph_changes` with the delta before it returns, and keeps each unplanned change with a reason or reverts it. The loop's ship step, the single writer, appends the kept ones to the delta with `node tools/graph/delta-append.mjs <delta> <changes.json>`: each `{ id, op, target, after?, why: <the reason>, slice?, origin: "unplanned" }`, never acknowledged (`appendChanges` in `lib/data/delta.mjs`). An id already in the file is left out, so a ship sent again writes nothing twice; a change that would not validate is refused and said, the others still go in; the file keeps its layout (after its last change, in its own indentation). The script takes the delta's lock (`lib/data/delta-lock.mjs`: a directory beside it, `<file>.lock`, waited for 30 s, broken past 60 s, the one `serve` takes to acknowledge), so no two writers interleave a read and a write, and replaces the file through a temporary file renamed over it. It prints `DELTA ok added=… already=… refused=…` (then `DELTA refused <id>: …` per refusal), `DELTA none` when there is no delta at that path, or `DELTA bad …`. An architecture target goes to the delta's `architecture` list, the others to `data`. A delta inside one of the run's repositories is written in the ship worktree and committed on that repository's run branch, the delta alone, so the PR carries it (a session commits it on the issue's branch); one outside them all is written in place (`workflows/README.md`, "The delta is committed on the run branch"). `<changes.json>` may also be another version of the delta: its unplanned changes are appended, each without its acknowledgement (the loop's merge of a delta changed on both sides). Those changes then show in the Data tab (the Architecture tab for an architecture one) as unplanned and unacknowledged until the owner acknowledges them under `serve`.

The tool is **confined**: an agent chooses its `delta`, so it reads only a delta beside the specs of a project root, as the server writes them. The path is plain and relative to the project root (`docs/specs/<name>.delta.json` for the hub or a repository at the root, `<repo folder>/docs/specs/<name>.delta.json` for a repository's own), and its real file, symlinks resolved, must be `docs/specs/<name>.delta.json` inside that root, within the size limit. Anything else (an absolute path, `..`, another extension or folder, a symlink out, a missing or unreadable file) gets one refusal that says nothing about the file, so the tool can neither read another file nor tell whether one exists. The same rule holds from the shell (`graph.mjs changes --delta`, the same tool). `graph.mjs render --delta` and `serve --delta` read the path you type, wherever it is, and draw it; one outside the specs is never written.

`graph_data` (and `graph.mjs data`) answers with the stores (dialect and how it is known, how each declaration was read, counts, conflicts, extractor failures), one store's entities, or one entity with every field, key, index and foreign key and their `path:line`. An extractor that throws loses that file's or folder's facts and is reported by `graph_status`, `graph_index` and `graph_data`; the index goes on. A name or value from a file that holds a line break or another control character is printed JSON-quoted (`"a\n  + b"`) by `graph_data` and `graph_changes`, so it cannot forge a line of the answer. Like the rest of the graph, these are leads: open the `path:line` before relying on them.

## Freshness

`graph_index` re-parses only files whose size or mtime moved and whose content hash changed, drops deleted files, and re-resolves the edges of a repository that changed. The files the data model reads are tracked the same way, and a data job (a file, or a migration folder) runs again only when one of its inputs changed: an edited or deleted migration re-runs its folder. An index built by another grimoire version (its schema differs) is rebuilt in full, on the next query or index. Every query first checks (stat only) whether files moved and refreshes incrementally if they did, at most every 15 s per process. A project that was never indexed is not indexed implicitly by a query: the first `graph_index` installs the parser runtime and can take a while on a large tree.

Indexing is always this script, never a model. Three things run it:

- **After every subagent**: the plugin's `SubagentStop` hook runs `graph.mjs refresh` in the background, so the graph follows each implementer's commit and each integrate merge of the build loop. `refresh` builds the first index when `grimoire.config.json` has a `graph` block, and does nothing when the graph is disabled or was never set up.
- **Before a query**, as above.
- **By hand**: `graph_index`, or `npm run graph -- index`.

One indexer runs per index at a time (a lock next to it). A second one does not wait: it marks the index pending and the running one goes again before it finishes, so no change is lost.

**Worktrees.** Each checkout has its own index, since each branch has its own code (`lib/freshness.mjs`).

- *Its base.* The first of these branches that another checkout of the repository has checked out with an index: `baseBranch` in the config (`origin/dev` → `dev`), the branch's upstream when it names another branch, `origin/HEAD`, then `main`, then `master`. Otherwise the main checkout, whatever it holds. A branch stacked on `dev` is based on the checkout holding `dev`.
- *Seed.* A checkout with no index yet starts from a snapshot of its base's (`VACUUM INTO`), then re-parses only what its branch changed. Without `repos[]`, the one repository is named after the main checkout in every worktree, so the copied rows match.
- *Re-base.* Each index run, under its lock, first checks whether HEAD moved since the last index (a pull, a rebase, a merge of the base). If it did, it counts the files to re-parse from its own index (`git diff --name-only <indexed commit> HEAD`) and from the base's, and copies the base's index in one transaction when that saves at least 20 files (`GRIMOIRE_GRAPH_REBASE_MIN`). So once work is merged into main and main's index has it, a worktree that picks it up copies instead of parsing. The incremental index that follows makes the result match the working tree either way: re-basing changes the cost, never the answers. `graph_status` names the base, in `meta('base')`.
- The base's index is refreshed by its own checkout (its sessions, its hook, `refresh --root`), never from a worktree.

The build loop's lanes live under `.worktrees/`, which is not indexed; the run branch they merge into is.

Measured on this machine: ripgrep (114 Rust files) 0.7 s, FastAPI (1,147 Python files) 1.4 s, Vite (1,576 JS/TS files) 1.5 s, full index.

## Configuration (`grimoire.config.json`)

```json
"graph": { "enabled": true, "repos": ["api", "web"], "dir": ".grimoire/graph", "exclude": ["generated/**", "fixtures"], "maxFileKB": 512, "architectureDir": "docs/architecture",
           "data": { "migrations": [{ "path": "api:db/sql", "dialect": "sqlite" }] } }
```

`data.migrations` states a migration folder's dialect (`sqlite`, `postgres` or `mysql`) when no config of its tool says it and its SQL carries no marker: `path` is the folder, relative to its repository, prefixed with `repo:` in a project of several. It wins over every other source of the dialect.

All optional, and read as every checkout sees it: a linked worktree without its own `grimoire.config.json` uses the main checkout's (`scripts/project-config.mjs`). Without a config the project root is one repository. `repos` defaults to every entry of the top-level `repos[]`; `exclude` adds to the built-in skips (dependencies, build output, caches, minified and generated files, `.d.ts`). `enabled: false` turns every tool into a pointer back to grep.

## The parser runtime

The plugin ships no `node_modules`. The first index installs the pinned runtime (`web-tree-sitter` + `tree-sitter-wasms`, ~50 MB, lockfile-checked with `npm ci --ignore-scripts`) into the user cache (`~/Library/Caches/grimoire/graph-deps/<lock hash>` on macOS, `$XDG_CACHE_HOME` or `~/.cache` elsewhere, or `$GRIMOIRE_GRAPH_DEPS`), once per machine. `tools/graph/node_modules`, when present (`npm ci --prefix tools/graph`, as CI does), is used first.

Indexing always runs in a child process with V8's Liftoff-only WASM tier: some grammars crash the optimizing WASM compiler of current Node, and that must never take the MCP server down. YAML at a base ref is parsed the same way, in a child process (`lib/data/readers/yaml-aside.mjs`).

The YAML grammar is in the pinned set for the data model only: no file is indexed as YAML code. Its external scanner was compiled as C++ and imports `operator new` and `operator delete` (and a vector's length error), which the pinned runtime does not export, so it fails on its first parse as shipped; `lib/deps.mjs` renames those imports, in the grammar's bytes before it loads, to the C functions they stand for (`malloc`, `free`, `abort`), with the same signatures. Every other grammar loads unchanged.

# Review the implementation

Review the diff against its issue with an independent reviewer (never the implementer), in two gates, as strictly as the issue's **execution policy** says (`workflows/policies.md`, resolved as `implement` did):

- **`fast`** (a session's default when no floor or raise applies): one review covering the spec and adversarial-QA lenses together, one fix round for blockers and majors carrying every finding, minors to the PR description, then no re-review: re-run the tests and check each finding is addressed in the fix's own diff (the guard's job). Anything still open, or a test weakened, escalates to `strict` on the same branch.
- **`balanced`**: the two gates below, with the lenses that fit the repository. A session has no terminal sweep, so its quality gate also runs the terminal lenses that fit the repo's tags (reliability, privacy, and on a UI repo human interface, accessibility, store review).
- **`strict`**: the same, plus the lenses `policies.promote` names for the files the change touches (privacy for auth, session and secret paths; data-integrity for migrations and schemas; contract for API and event schemas), and data-integrity and contract when it depends on another repository's issue. That is the only promotion rule by file; input the code does not control (below) adds its own lenses in every profile. A change whose diff adds, removes or changes an auth check is `strict` with privacy, whatever its files are named.

The gates:

**Spec gate.** One reviewer, the spec hawk: does the diff do exactly what the issue says, nothing missing, nothing smuggled in, happy path working end to end? The repository's own rules are part of the issue: the spec hawk reads its `AGENTS.md` and `CLAUDE.md` invariants and golden rules, and a change that breaks one is a major.

**Quality gate.** A panel of lenses run in parallel, each applied only to the repositories it fits and each failing only on blocker or major findings: reliability and release readiness (hot paths, query patterns, backpressure, backwards compatibility, deploy ordering); eventing and data integrity (idempotency, ordering and replay, migration drift); adversarial QA (races, offline, forged input, abuse vectors, a new limit or check that a retry, resend or second path skips, or that runs after what it guards, or on a different reading of the input than the use it guards (a text filter in front of an engine that splits statements differently), plus dead code the change left behind); cross-repo contracts (both sides agree, release ordering stated); human interface craft; accessibility; privacy and hard authorization; store or platform compliance where the product ships through one. The lenses live in `workflows/personas/`; reuse them here.

**Input the code does not control.** Not a promotion by file: a property of the change. A change that reads or runs what someone else wrote (a repository's files, an upload, a payload) gets adversarial QA with a security review, and the reliability lens, whatever its profile. The reviewer times the hostile shapes `tdd` lists, follows a planted secret to every output, and checks code that models another tool's output against that tool, run on inputs the reviewer chose rather than only the implementer's fixtures. A review with only the reliability lens once missed that repository SQL could make a migration replay write a file; a security review outside the panel found it.

**Before the panel, a precheck.** Confirm there is something to review: a commit range, a non-empty diff, no conflict or stub markers added, tests moved with the behaviour. If any check fails, send it back before paying for reviewers. The loop does this with a cheap agent (`workflows/briefs/precheck.md`).

**Changes to stored data outside the plan.** A change the design's delta does not plan is never a finding by itself: the implementer kept it with a reason or reverted it, the PR lists it, and the user acknowledges it in the Data tab. Judge it on its merits like any other change: one that drops a column, an index or a table another repository still reads, or that loses data, is a finding at its severity; one whose kept reason does not hold is too.

Severity is a gate. Blocker and major send the work back; minor and nit are recorded for the human and never buy a rework round. A FAIL names at least one finding with `path:line`. "Fix everything" from the user does not change that: minors ride along with the next round a major already bought, or go to a ticket, never a round of their own.

**Verify a blocking finding before it buys a fix.** Check each blocker or major against the code. Overturn a finding only with a cited counter-fact (the check it says is missing is at `path:line`), and report the overturned ones rather than dropping them. The loop does this with a verifier (`workflows/briefs/verify.md`). A reviewer whose findings keep being overturned is a lens for `crystallize` to recalibrate.

Route every failing finding back to the implementer and re-review, bounded: three fix rounds per change, in the unattended loop (per stage, with a cheap guard deciding whether the whole panel must re-run) and in a session alike. In a session, count every source of findings on the PR against the same three: a re-review, a bot, a PR review, a later panel. At the cap, stop and hand the remaining findings to the user with what each would cost, rather than starting a fourth round. Re-review only the lens that failed, not the whole panel again, unless the fix touched what another lens judged. Always end on a review. Never start the repo's gate on a head that is still under review: gate the head that passed.

**A fix must not weaken a test.** On every re-review, read the fix's own diff (the head before the fix to the head after it), not only the whole change: a test the change added and a fix then loosened looks, in the whole diff, like one weak test that was always there. A test that existed before the fix and proves less after it (an assertion removed or loosened, an expected value changed to match what the code now does, a test skipped, focused or deleted) is a blocker, unless a finding said that test was wrong or asked for the behaviour its new expectation encodes. The loop does this with a fact sheet of the fix diff (`workflows/briefs/guard.md`).

On PASS the PR is ready once every review thread on it, from bots and humans alike, has an explicit resolution (fixed with a commit, tracked with a ticket, or declined with a reason). Then merge per your merge policy. **Next:** `crystallize`, so the harness learns from the PR and its threads, then ship.
